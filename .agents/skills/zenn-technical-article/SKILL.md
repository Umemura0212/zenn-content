# Zenn技術記事の執筆・品質レビュー

## 目的と読者
- 想定読者は、関連技術の基礎を知る開発者。事前知識が必要なら冒頭で示す。
- 記事は約5分で全体像と設計判断がわかる「入口」。時間や文字数を優先して根拠を削らない。
- 1記事につき1つの問いに答える。複数の技術を扱う場合は、その関係と選択基準を中心にする。

## 執筆の優先順位
1. **読者の利益**：冒頭で「どんな課題を、何を判断できるようにする記事か」を伝える。
2. **根拠**：公式仕様、開発元の技術記事、標準・原著を優先。重要な事実と引用元を近くに置く。記事本文を実際に確認し、URLの存在と主張の対応を確かめる。未確認・無関係な参考資料は削除。
3. **独自の価値**：既知の技術と、この解説の新しい視点・比較・設計上の判断を区別する。技術そのものの新規性を誇張しない。
4. **説明の深さ**：問題→仕組み・全体像→具体例→適用条件・限界まで。詳細なコード、設定値、周辺知識の網羅は不要。
5. **明瞭さ**：結論を先に。一文一義・短い段落。説明的な見出し。用語の表記を統一。図は本文と整合する場合のみ使う。
6. **客観性**：主観・将来予測を事実と混ぜない。「私は思う」を避け、独自案は「設計案」「例」と明記。未実装の効果を実績として書かない。

## SNS・二次情報の検証

SNS投稿や第三者の解説は調査の起点とする。投稿は投稿者自身の意見・設計案の原典ではあっても、効果や標準仕様を証明する資料ではない。

1. 原文、投稿日、リンク先を確認する。原文を直接取得できない場合は制限を明記する。
2. 主張を「公式に確認できる仕様」「技術的な設計案」「未検証の経験談・数値・普遍的断定」に分類する。
3. 開発元の公式資料、原著論文、標準、公開された検証結果で個別に裏付ける。推論を公式主張として帰属させない。
4. 適用条件、反例、失敗時のコストを調べる。再試行回数、速度改善率、安全性の強い断定は独立した根拠がなければ採用しない。
5. 参考にしたSNS独自の案を示す場合、公式の根拠と別に区別する。長文の転載はしない。

効果を主張するなら比較条件と測定結果を示す。構成案は期待される利点と限界を併記する。

## 記事を書く手順
1. **企画メモ**：読者／一文の問い／一文の答え／既知の知識／この記事の付加価値を決める。
2. **根拠メモ**：主要な事実ごとに、一次資料のURLと該当箇所を確認する。仕様やプラン制限は適用条件も確認する。
3. **骨格**：冒頭で課題と答え。本文は3〜4個の主要論点。失敗例・比較例・判断表のいずれかで「なぜ」を見せる。
4. **推敲**：各節に「読者がここから何を判断できるか」を問い、重複・形式的なまとめ・根拠のない評価を削る。
5. **敵対的レビュー**：「反例は？」「適用できない場面は？」「図と表の条件は矛盾しないか？」「古いバージョンでも成立するか？」を点検。
6. **最終確認**：タイトル・本文・根拠・図・リンクが一致しているか確認する。必要ならZennのプレビューで表示を確認する。

## 品質ゲート（必須）
- [ ] 読者が最初の3段落で課題・答え・記事の価値を把握できる
- [ ] 事実／公式仕様／提案・推論を判別できる
- [ ] SNS由来の主張は一次資料を確認し、未検証の数値や断定を転載していない
- [ ] 主要な技術的主張を一次資料で確認できる。出典が言っていないことを帰属させていない
- [ ] 少なくとも1つの具体例・比較・失敗条件があり、設計選択の理由がわかる
- [ ] 重要な限界・反例・利用条件を欠いていない
- [ ] 用語、数値、状態遷移、図が本文や関連記事と矛盾しない
- [ ] 過剰な前置き、同義反復、主観、長い言い回しがない
- [ ] 参考リンクはすべて本文の主張を支え、閲覧・内容を確認済み

## 公開と安全
- `articles/*.md` に有効なZenn frontmatter（`title`, `emoji`, `type`, `topics`, `published: false`）。
- 企業・顧客・社内環境固有の情報、秘密情報、内部コードは載せない。公開GitHub上のDraft PRも第三者に閲覧され得る。
- 実行・性能・導入効果を検証せずに「確認済み」と書かない。
- 明示的な本人承認があるまでマージ・公開・追加課金・権限拡張をしない。
